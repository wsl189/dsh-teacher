# Agent Note: Windows desktop distribution and Release updates

Status: implemented

English | [中文](2026-08-25-windows-desktop-updates.zh.md)

## Problem

The repository's Windows path requires a Node and pnpm checkout, a complete build, and a browser launch. That is suitable for development but does not provide an installable application, a stable shortcut, or a controlled update path for users moving to a new Windows computer.

The product UI also has no state owned by an application distributor. A browser deployment cannot know whether its server process came from an installed package, which Release feed applies to it, whether an installer is downloaded, or when replacing application files is safe. Putting those facts into the ordinary Web Host would grant a remote browser a machine-level installation capability and would make non-desktop deployments carry meaningless controls.

The JavaScript application and its local AI service dependencies have different portability requirements. Electron can distribute the built DSH closure, but vLLM, MinerU, ASR servers, model weights, GPU drivers, and machine-specific plugin configuration require independent service and data lifecycle management.

## Decision

`apps/desktop` is an Electron application packaged as a per-user Windows x64 NSIS installer. The renderer keeps Node integration disabled and enables context isolation and sandboxing. It loads the existing Web surface from a private `127.0.0.1` server. A second `@deepseek-ai/dsh/desktop-backend` entry boots the ordinary `web` profile with browser opening disabled and an operating-system-assigned port, asks Connection to add the process launch token to the loopback URL, reports that URL over child IPC, and accepts one shutdown request. The Electron boundary accepts exactly one token query on that private origin; loading it exchanges the token for the ordinary authority-bound browser cookie before the redirect to `/`. The adaptive directory picker recognizes this Electron-hosted win32 process and mounts the in-app browser interaction, including for third-party fields such as a QQ bot workspace; standalone win32 Node.js Hosts retain the native system chooser. This avoids starting the packaged Electron executable as the native COM dialog worker. The Loader loads its public ESM resolver only inside the host fallback when Electron's embedded Node cannot expose the internal module importer, preserving each entry tree's package base and import conditions; client bundles retain Loader entry APIs without traversing the resolver's Node-only dependencies. Config-only HMR remains available while module HMR continues to require Node internals. The Electron process waits for complete profile disposal before ordinary quit or update installation.

Electron creates the hardened window and shows a script-free local startup document before it forks the backend. The startup document remains available while the child initializes the profile and is replaced only by a validated private-loopback launch URL. Backend readiness has no wall-clock deadline: an explicit fatal IPC message, fork error, or child exit rejects immediately, while a live child may continue through first-launch filesystem and antivirus work until it succeeds or the user closes the application. The packaged Windows-MCP runtime begins after launcher readiness and therefore does not hold the private Web page behind Python startup and tool discovery.

The renderer session grants microphone audio and clipboard writes only to the owning main frame at the validated backend origin. It denies camera, subframes, foreign WebContents, other origins, and unrelated permission types. Both Electron permission-check and permission-request handlers use the same rule and are cleared with the window.

The sidebar declares a distinct `sidebar.update` single seat beside `sidebar.settings`. `ui-desktop-update` occupies it only when the Electron preload exposes the narrow updater bridge. Checking snapshots render nothing; up-to-date snapshots render the installed version as a static footer status. Availability, download progress, completed download, and retryable failure render the matching action. The preload copies only validated discriminated update states and exposes state subscription, download, and install verbs. GitHub access, SemVer selection, checksums, file storage, and installer restart stay in the main process through electron-updater.

The ESM main bundle keeps electron-updater external and reads its lazy `autoUpdater` getter through the CommonJS default export. It does not use a named ESM import because Node cannot statically detect that getter as a CommonJS named export.

The updater provider is the public `wsl189/dsh-teacher` GitHub Releases feed. Automatic download is disabled: a user starts it from the visible update action. Prerelease installs may receive prerelease Releases, while stable installs do not. The generated `latest.yml` SHA-512 record is the downloaded-file integrity source; configured Authenticode credentials add Windows publisher verification and reputation.

`.github/workflows/windows-desktop.yml` builds an NSIS artifact on every branch push and manual dispatch using native Windows and Node 24. It starts the unpacked application, waits for the main window, discovers the authenticated private-backend URL from the desktop log, exchanges its token without following the redirect, and requires the authenticated `directoryPicker/list` Remote to return a valid listing. It then creates a `standard` preset Session through the packaged Host and requires `/goal` and `/plan` in its command directory before retaining the artifact. Failure diagnostics redact launch tokens. A `v<version>` tag must equal the shared root package version before the workflow publishes the installer, blockmap, channel metadata, and a SHA-256 checksum list to a GitHub Release. Ordinary commit builds remain workflow artifacts and never enter the client update feed.

The installer includes Electron, its embedded Node runtime, the built frontend, and the DSH production dependency closure with `asar` disabled so dynamic plugins, workers, subprocess entries, and native addons remain real files. Dependency-wide file filters remove source maps and TypeScript incremental compiler state from workspace-linked and registry packages before NSIS compression; neither artifact participates in the installed runtime. The desktop manifest lists every required workspace peer and workspace dependency that electron-builder cannot collect transitively. It also directly anchors `turndown` and `@joplin/turndown-plugin-gfm`, whose executable entries are required when the standard preset dynamically imports `@deepseek-ai/dsh-tool-web`; this prevents the packager's pnpm workspace collection from ending that runtime dependency branch at the Loader-resolved package. The payload gate requires both entries and Turndown's `@mixmark-io/domino` runtime in addition to checking every packaged workspace manifest for non-optional workspace dependencies and peers at the application root. The installer does not include vLLM, MinerU, ASR, model weights, GPU drivers, third-party profile configuration, or `%USERPROFILE%\.dsh` user data. Those services remain separately deployable, including through Docker, and the installed application uses their configured endpoints.

## Alternatives considered

**Produce one `pkg` executable.** The existing single-executable work packages a deliberately closed JSON-RPC runtime and excludes Windows. Extending it to the complete Web composition would require custom treatment for dynamic Loader package resolution, client assets, native addons, worker and subprocess files, and a self-replacement helper. It would recreate the update and installer lifecycle that Electron and NSIS already maintain.

**Put the complete application and GPU services in one Docker image.** Containers are useful for MinerU, vLLM, and ASR service reproducibility, but a Windows desktop container does not provide a native per-user GUI, shortcuts, browser isolation, or an ordinary self-update experience. GPU driver and host compatibility also remain outside the image. The desktop installer and service containers therefore solve separate deployment units.

**Expose update controls from the Web Host.** This would make the same network surface that serves a browser capable of replacing its host installation. The preload-gated seat keeps installation authority local to a packaged desktop process and leaves ordinary browser deployments unchanged.

**Raise the backend startup deadline.** A larger constant would retain a blank pre-window interval and would fail again on a slower machine or antivirus pass. The visible startup document makes the wait observable, while explicit child failure remains the terminal condition.

**Enable `asar` instead of filtering individual artifacts.** A single archive would reduce filesystem entries further, but Loader packages, subprocess entries, workers, and native addons require real paths in the current runtime. Keeping them unpacked preserves that behavior while suffix-level filters remove files with no installed-runtime role.

**Exclude source directories and alternate third-party builds with broad globs.** Package assets and Loader-resolved entries do not share one directory layout, so a directory-wide rule can remove executable content. The payload therefore removes only suffixes that are uniformly development-only; narrowing the file set further requires an explicit staged-runtime manifest that proves each retained path.

**Rely on electron-builder to retain every transitive registry dependency of a dynamic workspace package.** The pnpm workspace collector can preserve the workspace package while omitting an external package imported by its runtime entry. Direct desktop anchors plus executable-file checks make that dependency closure explicit without flattening every dynamic plugin into the Electron manifest.

## Consequences

- Windows users can install and update the repository build without installing Node or pnpm. Their DSH home remains separate and must be copied independently for a full machine migration.
- Each pushed commit spends a native Windows build, while only matching version tags publish update metadata. Release operators must advance the shared version before tagging.
- Unsigned builds remain functional but can trigger SmartScreen. Production distribution requires the two code-signing repository secrets and a certificate whose publisher identity remains stable across updates.
- The distribution is Windows x64 only. External AI services and GPU software retain their own installation, health, update, and storage procedures.
- The desktop Web server remains loopback-only and uses an ephemeral port, so the installer does not add a LAN-exposed code-execution surface or reserve a fixed local port.
- Users receive a window before profile initialization starts. A plugin that never settles can leave the startup document visible until the user closes the application; it cannot be distinguished from legitimate first-launch work by elapsed time alone.
- Installed builds omit source maps, so their stack traces refer to generated JavaScript; development builds retain source navigation. Removing maps and compiler state reduces NSIS extraction work and the number of files Windows security software examines.

## Testing

The desktop update-controller tests cover unpackaged current-version projection, prerelease selection, availability, manual download, progress, completed installation, hidden check failures, visible retry failures, and invalid actions. The runtime-adapter test exposes electron-updater only as a CommonJS default export and requires `autoUpdater` to resolve from it. Client tests cover isolation-boundary validation, observable subscription teardown, wide and rail current-version status, update actions, progress, restart, retry, browser-only suppression, late slot declaration, and plugin teardown. Sidebar tests pin the new seat declaration and its wide/rail owner share. The Web scenario injects the same preload API before the real shipped composition boots, confirms the current version beside Settings, checks that the available action replaces it in the same position, drives download and restart states, and captures both accessible snapshots. The QQ workspace scenario boots the real shipped composition with a seeded offline bot, opens its workspace action, and captures the real Host-backed in-app directory listing without a model call. App-boot and preset tests disable Loader internals and require config-owned and host-owned packages to retain ESM import resolution; HMR tests require exact config watches to remain live in that mode. Workspace constraints reject any non-optional peer missing from the complete `@deepseek-ai/dsh` production dependency graph. The desktop-payload verifier fixtures accept complete workspace dependencies, optional absent peers, runtime JavaScript, assets, and native addons while rejecting missing required workspace packages, nested source maps, and compiler state; its Windows runtime set pins Turndown, the GFM plugin, and Domino entry files. The Windows workflow builds the real NSIS target, validates that closure in `resources/app`, runs the application with isolated user data, requires its `DeepSeek Harness` window to open, exchanges the launch token, calls the authenticated `directoryPicker/list` Remote, creates a standard Session, and requires its command directory to contain `/goal` and `/plan`; it also rejects a missing installer or `latest.yml` before retaining or publishing artifacts.

Renderer-permission tests execute both Electron handlers and require audio-only microphone access for the owning loopback main frame, retained clipboard writes, denials for video, subframes, foreign renderers, foreign or malformed origins, and unrelated permissions, plus idempotent handler cleanup. Desktop startup tests require the local window to become visible before backend work starts, validate localized script-free startup markup, retain a healthy backend wait for 90 simulated seconds, reject explicit fatal and exit outcomes, and prove listener cleanup.

# Agent Note：后台试题切割队列

状态：已实现

[English](2026-08-24-background-question-cutting-queue.md) | 中文

## 问题

PDF 版面提取、语义分割、题图渲染与持久化原本由已挂载的试题切割组件持有。上传入口会一直阻塞到完整流程结束，教师无法继续提交下一份 PDF。离开模块后，唯一进度界面会被移除，后续重新挂载的界面也无法观察已经接受的工作。

试题切割还依赖浏览器持有的 `File`、PDF.js、canvas 渲染、当前父会话、所选目录和接受任务时可见的设置。可跨导航的设计必须保留这些值，同时不能让后续会话或变化后的界面选择改投已有任务。

## 决策

客户端插件在完整生命周期内持有一个 `QuestionCuttingController`。控制器是与 React 兼容的 observable，按上传顺序提供不可变进度行。入队时锁定浏览器 `File`、所选页码、目标目录、渲染设置，以及已经绑定当前父会话的分割执行器。挂载组件只提交请求并投影 observable；工作进程的执行不归组件挂载与卸载所有。

一个顺序工作进程依次处理已接受的 PDF。版面提取、语义分割、题图渲染与保存会按具名阶段发布单调递增的整数进度，同时报告已保存图片数和最终错误。等待行的计时保持为零；中间工作区用工作进程开始时间与最终结束时间计算活动与终态计时。确认页码面板后会立即清空本地选择，因此活动行继续处理时可以读取并加入下一份 PDF，后续任务以等待状态显示。

插件释放时会停止接收任务，丢弃尚未开始的工作，移除观察者，并等待活动任务结束后再释放控制器。队列与浏览器持有的源文件不会跨完整页面刷新或应用关闭持久化；已提交的图片分片仍是 Host 所有的持久数据。

## 考虑过的替代方案

**把队列保留在组件 state 或 ref 中。** 这种方案只能在同一组件保持挂载时支持重复上传，切换模块或会话仍会丢失所有权与进度投影。

**把每次切割做成持久 Host 作业。** 这需要为完整源 PDF 增加新的上传与恢复协议，或者把 PDF.js 与 canvas 裁剪流程移出浏览器。当前所需生命周期是 Web 插件持续运行期间的界面导航，因此只有未来明确要求跨刷新或进程退出恢复时才引入这项更大能力。

**并发运行全部已接受 PDF。** 并发 PDF.js 栅格化、OCR 请求、语义子会话和文档修改会提高内存消耗与资源争用。顺序执行仍允许连续提交，并为每个等待行提供明确位置，同时不会阻塞无关工作台操作。

## 结果

切换工作台板块或对话不会再取消、永久隐藏或改投已经接受的切割任务。返回试题切割后会观察同一组进度行、百分比与计时。较长队列会在浏览器内存中保留源 `File`，并且每次只执行一份 PDF。最终状态行在当前插件生命周期内保持可见，完整刷新后则从空队列开始。

## 测试

控制器覆盖会保持第一份 PDF 的版面提取未完成，再接受第二份 PDF，验证顺序执行，移除订阅者，并确认两个任务仍会结束；它还验证一份 PDF 失败后不会阻塞下一任务。组件覆盖固定中间区域的百分比、阶段与计时投影，并验证确认目标目录后会入队且不会禁用下一次上传。组装 Web 场景会挂起真实 MinerU 响应，提交两份 PDF，记录两行进度，再切换板块与对话，并确认这些进度行仍属于持续运行的插件。
